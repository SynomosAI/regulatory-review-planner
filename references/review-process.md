# 审查流程

本文件用于把旧接口式合规审查工作流转化为面向 WorkBuddy 的模型自主规划式审查。

## 可借鉴的旧流程

已观察到的接口流程大致如下：

1. 预取外部数据。
2. 创建审查任务。
3. 并发执行普通分组审查和专项审查。
4. 输出进度事件。
5. 返回 `review_completed` 和 `final_result`。

技能应借鉴这种“先拆解、再分组、后汇总”的思路，而不是照搬固定顺序。审查智能体应根据用户文档、当前任务材料、可用工具和审查目标决定哪些审查项真正需要执行。

## 自主规划

开始审查前，先形成简洁的内部审查计划：

- 文档类型和业务背景。
- 当前任务中已读取/需检索的材料。
- 必须覆盖的审查层。
- 由文本触发的专项审查。
- 需要的外部依赖，例如现行法规、上级制度、用户提供的模板或历史版本。
- 需要调用的律爱多工具，以及工具不可用时的降级标签。
- 输出深度：快速筛查、完整审查报告、Word 备忘录、修订说明、审批材料等。

只有在缺失信息会改变法律或业务结论，且无法合理假设时，才向用户提问。

## 审查轮次

复杂文档可分轮审查：

1. 完整性与结构轮：标题、制度层级、制定依据、适用范围、管理部门、生效日期、附件；识别应有模块、配套制度、执行责任人、审批路径、证据留存、投诉申诉渠道及制度间衔接缺口。
2. 权限轮：审批权、检查权、处分/处理权、部门职责、责任追究。
3. 法律风险轮：法规名称时效性、上级制度冲突、个人信息、劳动、公平竞争、知识产权。员工制度需将竞业限制、知识产权、个人信息按专项子项展开，避免仅给出笼统综合结论。
4. 一致性轮：编号重复、条款冲突、指代一致、条件设置、循环依赖。
5. 语言轮：制度语言、敏感表述、禁止性/强制性表述、错别字、数字和标点。
6. 汇总轮：合并重复问题并排序。

## 律爱多能力嵌入点

1. 输入阶段：优先使用“文档解析”读取制度正文、附件、页码和扫描件 OCR。
2. 背景阶段：需要对照用户提供的模板、历史审查口径或项目背景时，读取当前任务中可用材料。
3. 法规阶段：输出具体法条、效力状态或监管结论前，按授权使用 `mcp-law-search.search_article`、`law-pkulaw-mcp.get_law_list`、`mcp-law-search.get_article` 或 `fatiao-pkulaw-mcp.get_law_item_content`；涉及时效或条文准确性时，使用 `chat-web.adjust_provisions` 或 `law-recognition.law_recognition` 核验。
4. 案例阶段：用户要求裁判支持，或重大合规风险需要司法实践佐证时，按授权使用 `case-pkulaw-mcp.get_case_list` 或 `pkulaw-mcp-case-search.search_case`；已知案号时使用 `case-number-recognition.anhao_recognition`。
5. 主体阶段：制度适用主体、发文主体、供应商/交易相对方状态影响结论时，本期不作 MCP 核验，统一标记 `[主体信息待人工核验]`。
6. 交付阶段：用户要求批注、修订稿、留痕或版本管理时，使用“文档批注与修订”和结果保存能力。

## 严重程度判断

- **高**：法律依据失效；与上位法或上级制度冲突；越权设定处罚或权力；过度收集个人信息；歧视或公平竞争风险；条款可能无法执行或无效。
- **中**：缺少必要制度要素；审批或职责不清；内部条款矛盾；编号问题影响引用和执行。
- **低**：语言风格、标点、轻微引用格式、表述润色、非实质一致性问题。

## 重要区分

- “不适用”不等于“不合规”。
- 背景不足时，应标为假设或信息缺口。
- 同一条款可能在一个审查层合规、在另一个审查层有问题；最终按实质问题合并。
- 对高影响条款，优先给出可直接替换的建议文本。
