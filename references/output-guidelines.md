# 输出规范

## 默认审查报告结构

1. 审查备注：已读取材料、未核验事项和来源状态。
2. 结论：可以推进、修改后推进、需实质性重写。
3. 关键风险：列出 3-7 个影响最大的发现。
4. 问题表：
   - 优先级
   - 条款/命中原文
   - 风险说明
   - 法律依据
   - 修改建议
5. 修订建议：为关键条款提供替换文本。
6. 假设和待确认问题。

## Word 交付规范

默认交付为 Markdown 格式制度合规审查报告文件（`.md`），文件名建议为：`[制度名称]-合规审查报告.md`。开始生成任何交付物之前，应主动确认交付物组合：默认包含 `.md` 制度合规审查报告，并询问用户是否还需要同时生成其他格式或附加交付物。用户确认前，不得先生成 `.md`、Word 或其他交付物。Word 审查报告、Word 批注/修订版、修订说明和审批材料仅在用户选择或明确要求时作为附加交付；不主动输出技术化 JSON。用户选择 Word 审查报告或 Word 批注/修订版时，应生成 `.docx`，文件名建议为：`[制度名称]-合规审查报告.docx`。

Word 应采用正式、易扫描的法务备忘录版式：

1. 首页列示制度名称、文件版本（如有）、审查日期、审查结论和来源状态。
2. 使用“审查备注”“总体结论”“关键风险”“问题清单”“建议替换文本”“待确认事项”作为一级章节。
3. 默认使用五列表格：优先级、条款/命中原文、风险说明、法律依据、修改建议。法律依据单元格内按“法规名称第X条｜核心规则摘要｜[来源状态]”编排；不得为来源标签单设狭窄列。
4. 当某一问题需要呈现超过两项法律依据、较长原文或完整替换条款时，改用风险卡片式：风险等级与条款、命中原文、风险判断、法律依据、整改建议、建议条款依次纵向排布。不要为了塞进表格而将字号压缩到难以阅读。
5. 高风险行可使用克制的浅红色标识；中风险使用浅黄色；低风险使用浅灰色。不得仅以颜色表达风险等级。
6. 长原文和长建议允许换行；不得固定表格行高或压缩至难以阅读的字号。优先合并“建议替换文本”和“待确认事项”的连续排版，避免末页只剩少量项目；以三页左右为宜，但以可读性优先。
7. 页脚标示“制度合规审查”及页码；客户版正文不写入工具调用细节或内部运行状态。
8. 交付前必须渲染并检查每一页，确认中文字体、表格分页、页眉页脚和文字均无截断或重叠。渲染环境存在字体替换时，应修复字体设置或在审查备注中披露。
9. 对用户可见的结果目录只保留最终 Word 及用户明确要求的附件。版式校验产生的 PNG/PDF 必须写入系统临时目录并在交付前清理，不得与最终 Word 一并导出。

## 表达风格

使用清楚、可执行的法律产品语言。避免只写“表述不规范”之类的空泛判断；必须说明为什么有问题，以及如何修改。

面向 WorkBuddy 法宝版用户时，默认采用“法务审查报告”口吻：结论先行、风险分层、建议可执行。不要把工具调用过程写成技术日志；审查备注只说明已审阅材料、来源状态和待补充材料。

## 法律依据与建议条款

1. 每个高风险问题默认展示可核验的“法规名称 + 条款号 + 核心规则摘要 + 来源状态”。例如：`《劳动合同法》第39条第（二）项｜解除须以严重违反合法有效规章制度为前提｜[法宝 MCP 检索]`。
2. 同一问题有多部法规时，正文保留最强的 1—2 项依据；其余依据可放入附录，避免表格堆砌。
3. “整改建议”说明改什么、为什么改；“建议条款”提供可复制的完整文本。仅在事实、主体、用工地或上级制度不足以定稿时，才以待确认问题代替建议条款。

## 内部结构字段

内部组织问题清单时，可使用以下字段；用户侧默认不输出字段名、技术化 JSON 或代码块。生成 `.md`、Word、修订说明或审批材料时，应转换为自然语言、表格或风险卡片。

- `review_key`
- `review_name`
- `content`
- `is_compliance`
- `severity`
- `source_label`
- `detail`
- `suggestion`
- `proposed_text`
- `compliance_depend`
- `status`：`issue`、`pass`、`not_applicable` 或 `needs_context`

字段值和解释使用中文。仅在产品侧明确需要结构化对接时，才保留字段名。

## 审查备注写法

建议格式：

```text
审查备注：已读取[文件/附件]；[若适用] 未取得[上级制度/法规原文/案例]，相关结论标记为[待核验]。
```

仅在内部执行记录中保留工具调用明细；不得据此虚构“已核验”结论。

## 去重规则

多个审查项命中同一条款时：

- 只保留一个主问题。
- 列出相关审查项。
- 最强依据放在前面。
- 修订建议集中在同一处。

示例：引用已废止的《合同法》可能被 `institutional_basis`、`regulation_name_validity`、`external_organization_name` 和 `typo` 同时命中。最终只报告一次“法律依据失效/引用过时法律”，并在相关审查项中说明交叉命中。
## 客户版 Word 交付规则

- 首页应列示高风险、中风险数量概览，并写明审查结论、范围和来源状态。
- 客户版正文不得展示“工具未启用”“MCP”“能力开关”等内部运行信息；仅保留已审阅材料、来源状态和待补充材料。内部执行记录可单独留存。
- 横向问题清单表必须设置表头跨页重复，并为每一个数据行设置“不允许跨页断行”。生成后应检查每项完整内容均位于同一页，尤其是较长条款行。
- 表格正文优先保证可读性；如信息过长，应压缩重复表述或拆为卡片，不以过小字号强行容纳。
- “建议条款”按主题制作成独立分块，每块包含标题和完整示例条文，避免连续长段落难以定位。
